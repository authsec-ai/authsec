## 1. Migration runner facts

* `cmd/main.go:87-101`: GORM AutoMigrates `migration_logs`. Then `NewMasterMigrationRunner(MigrationsDir("master"), ...)` runs (skipped when `SKIP_MIGRATIONS=true`).
* `internal/migration/runner.go:61-88` loads `*.sql` from `migrations/master/` and from a sibling `migrations/permissions/master/` if that folder exists. It does not exist. Files are sorted by their numeric prefix.
* **`migrations/deltas/` is NOT applied.** The runner never reads it, and its file names have no numeric prefix, so `parseMigrationFileName` would reject them anyway (runner.go:126-138). The headers say "Run once against a LIVE database: `psql "$DATABASE_URL" -f ...`" (for example `deltas/governance_sod.sql:3`). Commit 568e818 (2026-07-31) says: "Removed migrations/deltas/ (never read by the runner; content already in bootstrap)". New delta files were added again on 2026-09-10 (a3562f4, 6bb4577 and others). 026_governance_schema_parity folds six of the delta tables into a numbered migration. The other delta tables (sod_rules, sod_violations, certification_*, birthright_policies, entitlement_provenance, provisioning_instructions, discovered_agent_iga_links, discovered_agent_events) exist only in 001 + deltas. A DB bootstrapped before they were added to 001 gets them only through hand-run psql (**uncertain** which DBs are affected).
* **`migrations/contract/037_iga_access_edges_contract.sql` is NOT applied** (separate directory; see `.claude/specs/P2-EVIDENCE.md:181`).
* Leftover DB-per-tenant machinery still compiles but nothing calls it: `NewTenantMigrationRunner` (runner.go:48), `GenerateWorkspaceDBName` returns `tenant_<uuid>` (db_utils.go:232), `RunTenantMigrationsInProcess` (db_utils.go:255), `ApplyICPTenantMigrations` (icp_provisioning_service.go:48). `RunMigrations` still looks for `000_tenant_template.sql` (runner.go:145).

## 4. Row-Level Security / Postgres version

* RLS: **not used anywhere.** I grepped authsec and mt-plugin (`.sql` and `.go`) for `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL`, `CREATE POLICY`, `current_setting('app...`, `set_config`, `BYPASSRLS`, and found nothing. The only hit is `SET row_security = off;` in `mt-plugin/migrations/tenant/000_tenant_template.sql:18`, which is pg_dump boilerplate. `CLAUDE.md:77` lists RLS as an aspiration ("<!-- FILL: confirm DB -->"). `CLAUDE.md:129` reads like a decided fact ("Postgres 15; RLS ... ADR-0001"), but it is an example inside an HTML comment, and `docs/adr/` does not exist. **Do not treat it as evidence.**
* Tenant isolation therefore depends entirely on Go code adding `WHERE workspace_id = ?`. Only a subset of tables have DB-level defence, through composite FKs (the IGA family; spec invariant at 001:3746-3750, rule at 027:10-12).
* For RLS to work later: the app connects with a single pooled role (`config.Database.DB`, `config.DB`). If that role owns the tables, RLS needs `FORCE ROW LEVEL SECURITY` or a non-owner app role, plus a per-transaction `SET LOCAL app.workspace_id`. The schema blockers are the 12 nullable `workspace_id` columns, the 2 `text`-typed ones, the NULL-means-global rows, and the 10 tenant-ish tables with no workspace column.
* Version: PG15+ is required (see section 0). CI uses 15 and 16; dev and test use 16.

## 7. Evidence that challenges "workspace == tenant"

1. **Users are not strictly owned by one workspace.** `users.workspace_id` is nullable with no FK (001:1516). `workspace_memberships (workspace_id, user_id)` lets a user hold memberships in other workspaces, and `user_id` there has no FK to users (001:1659-1671). The model is closer to "home workspace + memberships" than a hard tenant wall.
2. **OAuth clients have no owning workspace:** `mcp_oauth_clients` has only `home_workspace_id` (nullable, `ON DELETE SET NULL`, 001:2633). `oauth_as_controller.go:1974,2022` says that authority comes from the resource server's workspace, "NOT the mutable home_workspace_id". Clients are effectively shared across workspaces.
3. **Platform-level rows sit inside the tenant tables** (NULL workspace: roles, permissions, oidc_providers, sod_rules, oidc_states for "platform-level login" at 001:681), plus a **system workspace** `00000000-…` (001:2915-2960). The two conventions conflict: 001:2882-2900 seeds `users:*` and `migrations:*` permissions under `sys_workspace`, while the app's admin seeding grants `permissions WHERE workspace_id IS NULL` (`database/admin_seed_repository.go:69`, and 003/005).
4. **Trust anchors are instance-wide:** `trusted_issuers` (no workspace) and `workload_identity_providers.issuer` (globally unique).

## 8. Top 15 findings (ranked)

1. **No database-level tenant isolation.** There is no RLS anywhere (section 4), so isolation depends entirely on app-side `WHERE workspace_id`. Composite FKs exist only for the IGA and cloud-graph families plus a few identity tables.
2. **The global `UNIQUE (resource_uri)` on resource_servers (001:2173) defeats the per-workspace unique (001:883).** It allows cross-tenant squatting and leaks existence.
3. **The global `UNIQUE (issuer)` on workload_identity_providers (001:996).** A shared issuer such as GitHub Actions can be claimed by only one workspace.
4. **Tenant data with no workspace column:** `services` (credentials and vault paths, scoped by `created_by`: `repository/extsvc_repository.go:57`), `credentials` (WebAuthn), `mfa_methods`, and the 9 `spire_*` tables (global `spire_policies.name` and `spire_workloads.spiffe_id` uniques at 001:2258,2260).
5. **OAuth clients (`mcp_oauth_clients`) have no owning workspace.** There is only a nullable `home_workspace_id` with `SET NULL`. `oauth_client_secrets` and `oauth_client_jwks` inherit this.
6. **Grant join tables have no workspace and use single-column FKs:** `role_permissions` (001:2714-2718), `mcp_tool_scope_map` (001:2603-2607), `oauth_scope_permissions` (001:2641; `permission_id` has NO FK). The DB allows a role in workspace A to hold a permission from workspace B.
7. **36 workspace-scoped tables have no FK to workspaces at all**, including users, roles, permissions, groups, service_accounts, resource_servers, cloud_connector and every audit table. Deleting a workspace does not cascade and leaves orphans.
8. **About 80 single-column FKs point at workspace-scoped tables** (cloud_* children → cloud_connector(id), discovered_agents → discovery_sources, birthright_policies → roles/groups/resource_servers, scim_events → scim_connections, …). This contradicts the rule written in 027:10-12.
9. **Nullable or mistyped scope columns:** 12 nullable `workspace_id` columns (users, roles, permissions among them), and `audit_events.workspace_id` and `spire_audit_logs.workspace_id` are `text` (001:189,1098).
10. **Two conflicting "global" conventions:** NULL workspace versus the system workspace `00000000-…` (001:2882-2960 versus `database/admin_seed_repository.go:69` and 003/005).
11. **Global uniques on per-user or federated secrets:** TOTP backup `code` (001:1452,1483), `spiffe_id` (001:965,1773), and the redundant global `device_token` (001:1392).
12. **Bootstrap parity is broken:** 22 tables and about 69 columns from 018-042 are missing from 001. 001 also still has single-column cloud FKs that 027 made composite. The header claims 80 tables; there are 162.
13. **Go queries 9 tables that do not exist** in the single DB: agents, attestation_policies, audit_icp_logs, certificates, workloads, workload_entries, workload_svids, voice_active_sessions, oauth_configs. These are leftovers of the per-tenant DB, and `GetWorkspaceDB` now returns master. Runtime reachability is uncertain.
14. **`migrations/deltas/` (14 files) and `migrations/contract/037` are never applied by the runner.** Ten governance tables exist only in 001 + deltas, so a DB that predates them depends on hand-run psql. `mfa_repository.go:35` runs DDL at runtime.
15. **The tenant→workspace rename was done in place in 001** (tenant_id count 259 → 0 between e9ccb83 and 67053a4), and it mis-renamed Entra's external tenant ID to `entra_workspace_id` (001:1320; JSON `entra_tenant_id`). `tenants.tenant_db`, `tenant_mappings` and `tenant_hydra_clients` were dropped. DB-per-tenant would have to be rebuilt, not restored: the mt-plugin template has diverged and still uses `tenant_id`.
