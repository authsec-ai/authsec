### A. /authsec/webauthn/** (all anonymous, routes.go:2019-2091) and the handlers they call
Shared facts:
- Every handler takes email plus body workspace_id (and sometimes client_id); none reads a token.
- Begin and finish are linked only by a challenge key `op:email:workspace_id` (webauthn_handler.go:129-131), which anyone can recreate.
- resolveDB/resolveDBWithError always return the global DB (webauthn_handler.go:142-161), so legacy FinishRegistration looks the user up by email only (:599).
- fetchClientForMFA ignores client_id (totp_handler.go:780-811).
- The Origin check is a header any non-browser caller can set.
- The auth-path rate-limit tiers never match, because selectRateLimitConfig checks "/uflow/..." prefixes while real paths start with "/authsec/" (mennanov_ratelimit.go:185-219). Only the general per-IP limit applies, and X-Forwarded-For spoofing defeats it (no SetTrustedProxies).

Findings:
- A1 P0 (b). Legacy passkey registration for any user, which also mints a token: POST /authsec/webauthn/beginRegistration then finishRegistration (also biometric/beginLoginSetup and confirmLoginSetup).
  - Needs only email + workspace_id (webauthn_handler.go:415-536, 554-795). The attacker completes a real ceremony with their own authenticator.
  - It sets mfa_verified=true (:738-765) and then calls WebAuthnRegisterInternal (:768, webauthn_token_generator.go:32-86), which mints a 24h token for the victim and returns it in the response (:792). No first factor is required: unauthenticated account takeover.
  - The token is also logged in plaintext (:773, :1057).
- A2 P0 (b). Forged attestation is still accepted. If go-webauthn FinishRegistration fails with an error containing "attestation"/"format"/"validation", buildFallbackCredentialFromContainer (fallback.go:14-52) stores the public key from the attestation object without verifying challenge, origin, rpIdHash or signature.
  - Locations: webauthn_handler.go:654-680, admin_webauthn_handler.go:489-524, enduser_webauthn_handler.go:~609.
  - Uncertain: which go-webauthn errors contain those words. Either way, A1 needs no forgery.
- A3 P0 (b). Admin passkey enrollment by email only: /webauthn/admin/beginRegistration and finishRegistration (admin_webauthn_handler.go:311-618).
  - The challenge key is `registration:email:admin`; it adds a credential and sets mfa_enabled/mfa_verified on any admin.
  - finishAuthentication then succeeds with the attacker's key (:732-899). It mints no token itself, but satisfies the admin MFA step.
- A4 P0 (b). End-user passkey enrollment by email + workspace_id + client_id: /webauthn/enduser/beginRegistration and finishRegistration (enduser_webauthn_handler.go:359-~730), with the same fallback.
- A5 P0 (b). TOTP enrollment for any user by email + workspace_id: /webauthn/totp/beginSetup|beginLoginSetup|confirmSetup|confirmLoginSetup.
  - The client supplies the secret it validates against (totp_handler.go:178-310, 311-450).
  - The attacker replaces or adds the victim's TOTP, adds "totp" to mfa_method, and receives the new backup codes.
- A6 P0 (b). SMS enrollment for any user: /webauthn/sms/beginSetup and confirmSetup (sms_handler.go:297-520) bind an attacker phone.
  - VerifySMS (:591-660) marks mfa_verified on the FIRST user of the workspace (`Where("workspace_id = ?")`, :640), not the verified user. P2 bug.
  - The code is not invalidated after use (replay for 5 minutes). Without Twilio the code is logged (services/webauthn_service.go:135-137).
- A7 P2 (b). Enumeration and MFA disclosure: /webauthn/{,admin/,enduser/}mfa/status and mfa/loginStatus (POST and GET ?email=&workspace_id=) return 404 for unknown users, plus the methods list and verified custom domain (admin_webauthn_handler.go:95-297, sms_handler.go:156-296, enduser_webauthn_handler.go:117-358).
- A8 P2. Broken endpoint: FinishBiometricLoginVerify (webauthn_handler.go:1772-1848) never loads the user's credentials and passes an already-consumed request body to FinishLogin, so it always fails.
- OTP verifiers are not stubs: TOTP uses pquerna/otp with a ±1 window (services/webauthn_service.go:38-58), and SMS uses a crypto/rand 6-digit code. Weaknesses: no attempt counters or lockout, no replay protection, and the rate limiting described above.

### D. Additional platform findings (from the platform sub-audit; [V] = re-verified by me)
- D1 P0 [V]. SAML signature is not enforced: internal/hydra/models/saml_methods.go:465-494. When signature validation fails, the code only logs "proceeding with caution" and still accepts the assertion; there are no Audience, NotOnOrAfter, InResponseTo or replay checks.

  - Result: code theft, then /oidc/exchange-code returns an admin JWT.
- D3 P0. generateAndRespondWithTokenAndOrigin calls GetAdminUserByEmail(email) without workspace scoping or ORDER BY (oidc_controller.go:903; admin_user_repository.go:455-478). Any OIDC login with email X can therefore get the admin token of the first workspace where X is an admin. Workspace admins can configure custom IdPs with arbitrary URLs.
